## 2. Ticketing system

The largest functional change. Tickets are stored in `report_issues`, created
from **Report an Issue**, and managed on the **Tickets** page.

### Ownership and visibility — now enforced server-side

**Before:** the frontend appended `?reported_by=<name>` and the backend trusted
it. Dropping the parameter returned every ticket, including internal notes. The
`PATCH` endpoint had no authorisation at all — the UI merely hid the buttons.

**After:** scope is derived from the auth token and the `reported_by` query
parameter is ignored.

| Role | Sees | Can change status / notes |
|---|---|---|
| admin / superadmin / fluidadmin | all tickets | ✅ |
| therapist | only their own | ❌ |
| sales | only their own | ❌ |

The response includes `canManage`, and the UI takes its permissions from that
rather than from a local role prop.

Ownership moved from `reported_by` (a display name) to `reported_by_user_id`
(a real user id). Renaming a user no longer detaches their ticket history, and
two people sharing a name no longer see each other's tickets. Existing rows were
backfilled by matching username/full name.

Identity on create now comes from the token, so a ticket cannot be filed as
someone else — a request claiming `reported_by: "admin"` is stored against the
authenticated user.

### Multiple screenshots

Up to **5 images, 5 MB each**. New table `report_issue_attachments`
(`ticket_id → file_url`), with a thumbnail grid and per-image remove in the form,
and a preview grid in the ticket detail drawer.

`screenshot_url` is kept in sync with the first attachment, so older tickets and
any un-refreshed browser tab keep working. Uploads reuse the existing
`/api/upload-file` endpoint one file at a time; if any upload fails the ticket is
not created, rather than being filed with missing evidence.

### Component dropdown now matches the sidebar

The old list was stale — it offered **Appointments** and **Reports** (neither
exists) and omitted **Payments** entirely. It is now role-aware and follows
sidebar order:

- **Admin:** Dashboard, Booking, Therapists, Clients, Payments, Settings,
  Notifications, Tickets, Other
- **Therapist:** Dashboard, My Availability, My Clients, My Bookings,
  My Calendar, Notifications, Tickets, Other

## 3. Payments / Refunds

### Cancellation and Refund tabs restored — `97499b9`

Three separate causes, all fixed:

1. **`/api/refunds` returned 500.** An `ORDER BY b.created_at` referenced a
   column that does not exist on `bookings` — the creation timestamp is
   `invitee_created_at`. Introduced in `9262382`; this 500'd every refund and
   cancellation tab.
2. **Pending tab** was genuinely empty (no rows in those states).
3. **Failed/Expired** returned rows the frontend then discarded.

Data corrections in the same commit:

- **Payment Gateway** read `payments.payment_mode`, which is NULL on every
  cancelled row. Now reads `payment_gateway_name`, with casing normalised
  (`razorpay` → `Razorpay`).
- **Order ID** was missing because organic bookings store it in
  `invitee_payment_reference_id`, not `razorpay_order_id`. Now falls back across
  both. Coverage went 0 → 12/12.
- **Timestamps** were blank because legacy rows have no `payments` row. Real
  source is `invitee_cancelled_at`. Coverage 34/34.
- Expired payment links no longer appear in **Cancellation** — they are written
  as `cancelled` + `payment_status='Failed'` by the expiry cron and belong on
  **Failed/Expired**.

### Expired and waiting-for-payment bookings — `2fd1485`

The Pending tab only matched `payment_pending` and missed
`waiting_for_payment` (the admin payment-link flow), so those bookings became
invisible after 30 minutes. Both statuses are now included.

### Known data gaps (not bugs)

On the Cancellation tab some rows legitimately show no amount or timestamp:

- **Free consultations** carry no amount by design (0 of 130 DB-wide have one)
- A few paid-type rows are **reschedules** where the payment sits on the
  successor booking
- `payment_status` is only written by newer booking flows
- `invitee_created_at` ("Booked At") is null on legacy rows and has no
  alternative source

## 5. API authentication — `1e25817`

**The API previously had no server-side authentication.** `authMiddleware` and
`requireRole` existed but were attached to **0 of 158 routes**, and `jwt.sign`
was never called, so no token was ever issued. Logging in only decided which
React components rendered; every endpoint answered anonymous callers from the
public internet — client records, bookings, therapist data and revenue included.

### What changed

- **Tokens** are issued by `/api/login`, the Fluidadmin branch, and
  `/api/verify-therapist-otp` (an auth entry point — the client logs straight in
  on its response). 24h expiry, configurable via `JWT_EXPIRES_IN`.
- **A single gate** registered before all route definitions: everything under
  `/api` requires a valid token unless explicitly allowlisted. Routes are
  **closed by default**, so adding one cannot silently expose it.
- **32 public routes** remain open — booking, payment checkout, webhooks,
  session notes, SOS, cron, and the auth entry points.
- **`requireRole`** applied to 13 destructive admin routes.
- **`lib/authFetch.ts`** patches `window.fetch` once at bootstrap instead of
  editing several hundred call sites. It attaches the token only to same-origin
  `/api` requests — never to Razorpay, MinIO or AiSensy — and clears the session
  and redirects on any 401.

### Credential handling

| Issue | Fix |
|---|---|
| `/api/update-password` and `/api/change-password` accepted a user id and a new password with **no proof of identity** — a one-request takeover of any account | Both now require and verify the current password |
| Passwords stored as **plaintext** | bcrypt on every write path; all 10 existing accounts migrated in place |
| `/api/verify-password` compared in SQL, matching only plaintext rows | Compares server-side, handles both formats |
| `/api/login` returned the **password hash** to the browser, which persists it to `localStorage` | Stripped from the response |

`panel-backend/migrate_hash_passwords.cjs` is idempotent and verifies each row
round-trips before committing.

## 6. Infrastructure

### `server/` removed — `e22ec9c`

A 102-route duplicate of `panel-backend` that was never deployed (absent from
`render.yaml`, `docker-compose.yml`, `vercel.json`, `Dockerfile.backend`). It
carried four unauthenticated auth endpoints comparing passwords in SQL, sitting
outside the new auth gate.

Only `/api/crm/todo` and `/api/crm-audit-logs` were reachable from the browser
via the Vite `/api/crm` proxy. Both exist byte-identically on `panel-backend`,
which already served them in production, so the proxy entry was removed and they
now fall through to `/api`. **Dev now matches prod.** −9,911 lines.

### Committed credentials removed — `14cfa99`

The live production database password was in **54 tracked files**, plus the host
IP and username. A postgres superuser connection string was in
`scripts/dump_bookings_schema.ts`.

- `lib/db.ts` and `panel-backend/src/db.ts` no longer fall back to hardcoded
  values — they now fail loudly. The old fallbacks silently pointed at the stale
  `safestories_db` whenever the env was missing.
- 45 standalone scripts read credentials from the environment. **Database names
  were deliberately left unchanged** — several target `ss_clone` /
  `safestories_v2`, and repointing them at production would be worse than the
  leak.
- `scripts/createUsersTable.ts` seeded a hardcoded plaintext admin password; it
  now takes `SEED_ADMIN_PASSWORD` and stores a bcrypt hash.
- `ssclone_env.txt`, `.env.production` and `panel-backend/.env.render`
  untracked; `.gitignore` now covers env files of every shape; `.env.example`
  added as the documented template.

> **⚠️ Still outstanding.** This stops the credential spreading further. It does
> **not** revoke it — the value remains in git history and on GitHub, so anyone
> who has cloned the repo still holds a working key to a database that is
> reachable from the internet. **Rotating the password is the only thing that
> closes this.** Deferred by decision.

## 7. Database changes

Applied automatically on boot; also available as
`panel-backend/migrate_ticketing.cjs`.

```sql
ALTER TABLE report_issues ADD COLUMN IF NOT EXISTS reported_by_user_id INTEGER;
CREATE INDEX IF NOT EXISTS idx_report_issues_owner ON report_issues(reported_by_user_id);

CREATE TABLE IF NOT EXISTS report_issue_attachments (
  id          SERIAL PRIMARY KEY,
  ticket_id   INTEGER NOT NULL REFERENCES report_issues(id) ON DELETE CASCADE,
  file_url    TEXT NOT NULL,
  file_name   TEXT,
  uploaded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_rin_ticket ON report_issue_attachments(ticket_id);
```

Plus backfills for ticket ownership and legacy `screenshot_url` values.

Two data corrections were applied to production during this work: booking
`696410` marked `payment_status='Failed'` (cancelled on payment-link timeout),
and `invitee_cancelled_at` backfilled for `696410` and `697179`.

## 9. Verification performed

Against a local backend on the production database before merge:

**Auth** — protected routes 401 without a token and 200 with one; garbage tokens
and a valid token with one character flipped both 401; all 32 public routes
confirmed still reachable unauthenticated.

**Roles** — a therapist token gets 403 on admin routes and 200 on shared ones.

**Tickets** — visibility matrix verified across 5 roles; the `reported_by`
bypass returns 0 tickets; identity spoofing rejected; a real PNG uploaded to
MinIO through the authenticated endpoint; 3 attachments round-tripped; both
notification types confirmed written to the database.

**Passwords** — each account's original plaintext was compared against its new
hash with `bcrypt.compare`. **9 of 9 comparable accounts verified unchanged.**

**Regressions** — no route was deleted; `requireRole` cannot lock out therapists
or sales (traced every calling component); `navigator.sendBeacon` in
`sessionDraft.ts` still works because its endpoint is in the public allowlist;
`/api/crm/todo` and `/api/crm-audit-logs` return real data through the new proxy
path; `vite build` passes.

All test tickets and test data were removed from production afterwards.
